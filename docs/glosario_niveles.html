Senior
Sobre "Medior": No lo inventaste — es un término real de la industria. Es especialmente común en los Países Bajos, Bélgica, España y Latinoamérica. Muchas empresas tienen el cargo oficial Medior Developer o Medior Engineer entre Junior y Senior. En inglés anglosajón se llama mid-level. La escala clásica es: Intern → Junior → Medior → Senior → Staff → Principal → Distinguished Engineer. Lo que sí hiciste fue usarlo para crear un marco de aprendizaje — eso es más valioso que conocer el nombre.
Junior

Fundamentos — hace con supervisión

Conceptos que un junior domina para ser productivo en el equipo. Con ayuda puede aplicarlos; solo, todavía comete errores.

Código y estructura

Naming conventions

Una sola regla para carpetas, archivos, Python y columnas Excel. El nombre dice qué es, no cómo se calcula ni de dónde viene.

En la industria
Guías de estilo (PEP 8, Google Style Guide). Equipos definen sus convenciones y las documentan.
En jass_system
UPPER_SNAKE_CASE en Excel · lower_snake_case en Python · NN_nombre en módulos.
Base

Conventional Commits

Formato estándar para mensajes de git: tipo: descripción. El git log se lee como la historia del proyecto, no como notas del programador.

En la industria
Estándar en proyectos open source y equipos medianos. Permite changelog automático y semantic versioning.
En jass_system
feat: generar_lista_multas con pago parcial rule · fix: cascada DEUDA_MULTA excluye CONVENIO
Base

Logging a archivo

Cada módulo escribe un run.log con timestamp, no solo print() a consola. El log queda en disco junto al Excel que generó.

En la industria
Observabilidad básica. Sin log, no hay forma de auditar qué pasó después del hecho.
Truco clave
force=True en basicConfig() y configurar dentro de main(), no a nivel de módulo.
Base

Validación de inputs

El primer bloque de código verifica que los archivos de entrada existen y tienen las columnas requeridas. Si algo falta, el error dice exactamente qué y dónde.

En la industria
Fail fast: mejor fallar al inicio con mensaje claro que fallar a mitad con error críptico.
En jass_system
Cada script verifica existencia del xlsx + columnas requeridas antes de procesar una sola fila.
Base

Diseño antes de código

Nunca escribir código sin README y arquitectura completos. El costo de cambiar un diseño es una línea de texto. El costo de cambiar código es horas.

En la industria
RFC (Request for Comments) · Design Docs · ADR. Los equipos serios diseñan en papel antes de codificar.
En jass_system
README → arquitectura.html → formato_*.html → código. En ese orden, siempre.
Base

Separación de responsabilidades

Cada módulo hace una sola cosa. Si necesitas "y" en la descripción del módulo, probablemente son dos módulos.

En la industria
Single Responsibility Principle (SRP) · "Do one thing, do it well" (Unix philosophy).
En jass_system
generar_lista / aplicar_penalidad / seguimiento — cada uno con una responsabilidad clara, un solo output.
Base

Lo manual es el ancla

Ante cualquier problema de diseño, preguntarse: ¿cómo lo resolvería una persona con papel y lápiz? El código que imita ese proceso es más fácil de auditar y corregir.

En la industria
"Make it work, make it right, make it fast" (Kent Beck). Empezar por el proceso manual no es limitante — es la base.
En jass_system
La tesorera cobró en papel antes de que el sistema existiera. El sistema imita ese proceso exacto.
Mentalidad

Una sola fuente de verdad

Si un archivo es usado por varios módulos, vive en shared/. Si una regla está documentada en dos lugares, solo debe estar en uno.

En la industria
Single Source of Truth (SSoT) · DRY (Don't Repeat Yourself). El duplicado diverge — siempre.
En jass_system
registro_cortes.xlsx vive en shared/ — tanto 6_corte como 6b_corte_multas lo leen del mismo lugar.
Arquitectura
Medior / Mid-level

Módulos completos — trabaja solo

Un medior toma un módulo de cero y lo lleva a producción sin supervisión. Entiende los trade-offs y elige entre opciones con criterio.

Proceso de diseño

Documentation-Driven Design

El README se escribe antes que la arquitectura visual y el código. Si no puedes explicar el módulo en texto claro, no puedes diseñarlo bien. La arquitectura es el resumen del README — no al revés.

En la industria
Readme Driven Development (TDD for docs) · "Write the README first" (GitHub culture). Fuerza claridad antes de comprometerse con código.
En jass_system
README → arquitectura.html → formato_*.html → código. Si README y arquitectura se contradicen → el README manda.
Proceso

HTML como contrato de diseño

Un HTML aprobado en conversación es una especificación visual que el código debe replicar exactamente. No se codifica sin el contrato. No se modifica el contrato sin aprobación.

En la industria
Wireframes · Figma mockups · Storybook components. El principio es el mismo: diseño visual antes de implementación.
En jass_system
formato_lista_corte.html define las 15 columnas, colores y anchos. openpyxl los replica. Un cambio en el Excel requiere actualizar el HTML primero.
Proceso

Evaluar 3+ enfoques antes de elegir

Nunca codificar la primera idea. Explorar al menos 3 soluciones distintas, definir criterios de éxito, y elegir con evidencia. El costo de explorar es cero; el costo de cambiar enfoque con código escrito es empezar desde cero.

En la industria
DORA, ADR (Architecture Decision Record). Los equipos maduros documentan qué descartaron y por qué — no solo qué eligieron.
Caso real
motor_matching v1 implementó la primera idea (enfoque de reportes). La versión correcta nació de "¿cómo lo haría manual?". Semanas perdidas.
Proceso

Método CRAD

Antes de escribir el prompt al LLM: Contexto (qué archivos, qué columnas), Realidad actual (qué datos fluyen hoy), Ambigüedades (casos borde no resueltos), Decisiones (qué archivos genera, quién los consume).

En la industria
Problem framing antes de solution finding. Un problema bien formulado es 50% de la solución.
Cuándo aplicar
Cualquier módulo nuevo o feature importante. Lo que queda en blanco en A y D son exactamente las preguntas que hay que resolver antes de diseñar.
Proceso
Calidad y confiabilidad

Idempotencia

Diseñar operaciones que producen el mismo resultado al re-correr. No acumular (+=), sino asignar (=) condicionalmente. Permite re-correr sin miedo cuando algo falla.

En la industria
HTTP PUT vs PATCH · REST idempotency · Database upserts. Cualquier API que se pueda reintentar debe ser idempotente.
En jass_system
Todos los módulos usan SET (asignación), no ADD. Re-correr generar_lista_multas 5 veces produce el mismo lista_multas.xlsx.
Calidad

Test de integración con fixtures sintéticos

Test que corre el módulo completo con datos de prueba que activan cada regla, sin tocar producción. Monkey-patch de config antes de importar main para redirigir paths a carpeta temporal.

En la industria
Integration testing con test databases · Docker containers para aislar estado · pytest fixtures. El principio: nunca verificar editando archivos reales.
En jass_system
test_6_corte_integracion.py: 1 caso por regla (SALVADO, CORTADO, EXONERADO, reclamo) · _tmp_test/ se borra al inicio → idempotente.
Calidad

Lifecycle de archivos

Documentar qué se borra (temporales), qué permanece (outputs del mes), qué se reemplaza (estado persistente), y qué es sagrado (inputs manuales que el operario llenó).

En la industria
Data retention policies · Artifact lifecycle management · "What can I delete without breaking anything?"
En jass_system
Temporales: _tmp_*/ · Outputs del mes: outputs/lista_multas.xlsx · Sagrado: registro_cortes.xlsx, planilla_mes/.
Arquitectura

Registro de auditoría vs vista operacional

La fuente de verdad (audit) solo crece y nunca se filtra. La vista operacional es una proyección filtrada para un consumidor específico, regenerable desde el audit cuando cambian los criterios.

En la industria
Bronze/Silver/Gold layers en data lakes · OLTP (fuente) vs OLAP (vista) · Event store vs read models en CQRS.
En jass_system
pagos_yape_pagaste.xlsx = auditoría (todos los egresos JASS). pagos_yape_devolucion.xlsx = vista (solo devoluciones para 5_cobranza).
Arquitectura

Preservación en 3 capas

En sistemas donde humanos y automatización comparten archivos: (1) backup antes de regenerar, (2) leer decisiones humanas antes de sobreescribir, (3) set de ya-procesados para no revertir trabajo confirmado.

En la industria
Optimistic locking · Versioning de datos · "Sagrado vs regenerable". El trabajo humano tiene costo real — el sistema debe protegerlo.
En jass_system
Módulo 4_pagos: backup_con_timestamp() + leer_decisiones_humanas() + set ya_confirmados. Re-correr 10 veces: el trabajo del operario sobrevive.
Calidad

Migración segura de schema

Cambiar las columnas de un archivo sin perder datos manuales. Protocolo de 7 pasos: backup primero, guard en el script, idempotente (detecta si ya migrado), leer por nombre de columna (no por posición), probar en 1 archivo antes de N.

En la industria
Database migrations (Alembic, Flyway) · Zero-downtime deployments · Blue-green deployments. El riesgo más alto: datos que los usuarios ya llenaron.
Caso real
módulo efectivo junio 2026: import con side effects sobreescribió 7 archivos con datos manuales. output consolidado como plan B los recuperó.
Calidad

Thin layer of shared primitives

shared/utils_*.py solo contiene funciones puras sin lógica de negocio. La orquestación (orden de pasos, qué columnas, cuándo aplicar) vive en cada main.py. Regla del Tres: no abstraer hasta tener 3+ usos genuinamente idénticos.

En la industria
Standard library design · Lodash vs Ramda · "Make the common case easy, the hard case possible". Una abstracción con if modulo=="X" ya no es una abstracción.
En jass_system
shared/utils_*.py: backup_con_timestamp(), normalize(). Orquestación: en cada main.py por separado. El test: ¿necesita if modulo == "X"? → no compartir.
Arquitectura

Pipeline order = business reality

El orden de los módulos debe coincidir con el flujo real del negocio, no con la conveniencia técnica. Si en la realidad el cliente recibe la boleta antes de pagar, 3_boletas va antes que 4_pagos.

En la industria
Domain-Driven Design (DDD) · "Make the implicit explicit" (Eric Evans). El código que contradice el negocio es técnicamente correcto pero semánticamente roto.
En jass_system
0_padron → 1_lecturas → 2_planilla → 3_boletas → 4_pagos → 5_cobranza → 6_corte → 6b_corte_multas → 7_cierre.
Arquitectura
Senior

Arquitectura del sistema — protege el negocio

Un senior diseña los invariantes que hacen que el sistema sea confiable cuando las cosas salen mal, cuando escala, o cuando el operador comete un error.

Patrones de resiliencia

Guard / Phase Gate

Centinela que bloquea la ejecución con sys.exit(1) si una precondición falla. El phase gate es un guard específico: bloquea re-ejecución de un script después de que el ciclo fue comprometido (commit point).

En la industria
CI/CD gates · Database transaction guards · Saga pattern checkpoints · "Don't let broken state propagate".
En jass_system
audit_penalidad APLICADO = sentinel del phase gate · auto-libera al cambiar MES_ANO · F1-4: sin gate, el pago post-commit habría sido revertido silenciosamente.
Resiliencia Día 1

Journal (Log append-only)

Registro de operaciones que solo crece. Nunca se edita. Los eventos son primarios; el estado actual es derivado (APLICADO − REVERTIDO = SET_TIENE). Permite reconstruir cualquier estado pasado y auditar exactamente qué ocurrió.

En la industria
WAL (PostgreSQL) · Kafka topics · Event Sourcing · Libro diario contable · Blockchain. El principio invariante: nunca mutar el pasado.
En jass_system
audit_penalidad.xlsx con columna ACCION. La reconciliación bidireccional lo usa para calcular quién realmente tiene el cargo aplicado vs quién debería tenerlo.
Resiliencia Día 1

Reconciliación bidireccional

En scripts que modifican archivos compartidos: comparar SET_DEBE (quién debería tener el cambio) vs SET_TIENE (journal: quién ya lo tiene). Aplica nuevos, revierte sobrantes, skipea correctos. Siempre converge al estado correcto.

En la industria
Reconciliation en contabilidad · Eventual consistency en sistemas distribuidos · "Desired state vs current state" (Kubernetes).
En jass_system
aplicar_penalidad.py v2: 10 cargos erróneos (4 CORTADOS + 4 EXONERADOS + 2 con reclamo) se revirtieron automáticamente al re-correr — sin intervención manual.
Resiliencia

Sidecar (change detection)

Archivo pequeño junto al archivo de datos que responde "¿cambió?" sin abrir el archivo grande. Contiene: hash de contenido, n_filas, timestamp. El guard lee primero el sidecar (O(1)); solo si cambió abre el xlsx (O(n)).

En la industria
Kubernetes sidecar containers · HTTP ETags · Archivos .sha256 en ETL · Rsync checksums. El patrón es universal: metadata separada de los datos.
En jass_system
Pendiente. Implementar cuando guards deban detectar cambios en planilla_mes sin abrirla. No implementar prematuramente.
Hardening Pendiente

Incremental Processing

Solo procesar el delta: registros nuevos o cambiados desde la última corrida. Combina sidecar (¿cambió el input?) y journal (¿qué ya procesé?) para saltear lo que no cambió.

En la industria
Kafka consumer offsets · Spark checkpoints · CDC (Change Data Capture) · "Only the delta" = la diferencia entre escalar y no escalar.
En jass_system
Pendiente. Aplicar cuando haya multi-JASS o >10k predios. Requiere sidecar implementado primero. Hoy con 239 predios el re-procesamiento completo es aceptable.
Hardening Pendiente
Diseño de sistemas

Estado persistente con semántica de negocio

Cada valor en una columna de estado tiene una razón de negocio, no solo un valor binario. CORTADO ≠ EXONERADO aunque ambos excluyan. En 6 meses, alguien leerá el historial y necesita entender por qué, no solo si.

En la industria
State machines con semántica explícita · DDD aggregates con invariantes · "Make the implicit explicit". Los estados son lenguaje — el lenguaje impreciso acumula ambigüedad.
En jass_system
registro_cortes.xlsx: CORTADO (deuda impaga) · EXONERADO (local comunal o especial) · REACTIVADO (volvió al flujo). El supervisor ya cargó EXONERADO antes de que el código lo soportara.
Diseño

Ciclo de vida de 3 fases

BORRADOR → PUBLICADA → COMPROMETIDA. Cada fase tiene permisos distintos sobre la lista. El commit point es el momento donde los efectos externos se vuelven irreversibles — después de ese punto, el sistema bloquea re-ejecución automáticamente.

En la industria
Order lifecycle (DRAFT → CONFIRMED → FULFILLED) · Git branches por entorno · Blue-green deployment phases. El commit point es cuando el dinero real cambia de manos.
En jass_system
6_corte: BORRADOR (generar) → PUBLICADA (secretaria anuncia) → COMPROMETIDA (aplicar_penalidad corrió). Después del commit: phase gate bloquea generar_lista.
Diseño

Blast radius contenido

Un constraint en un módulo no cascadea a otros módulos que no lo necesitan. El phase gate en 6_corte no afecta 5_cobranza ni 2_planilla. Alta cohesión dentro del módulo, bajo acoplamiento entre módulos.

En la industria
Bulkhead pattern (Circuit Breaker) · Microservices isolation · "Fail locally, don't cascade". La catástrofe contenida es manejable; la catástrofe en cascada no lo es.
En jass_system
6_corte y 6b_corte_multas tienen phase gates independientes. Un ciclo comprometido en uno no bloquea al otro. Los módulos upstream (2_planilla, 5_cobranza) no ven el gate.
Diseño

El sistema recuerda, no el humano

Cada restricción de negocio que no está en código es un bug esperando ocurrir. Si el operador debe recordar no re-correr el script después del commit, eventualmente lo olvidará. El phase gate elimina esa posibilidad para siempre.

En la industria
Poka-yoke (error-proofing en manufactura japonesa) · "Make illegal states unrepresentable" (Elm/Haskell) · Defensive design. La memoria humana no escala; las restricciones en código sí.
Caso real
El operador pasó 2 horas en el ciclo de junio tratando de no cometer el error F1-4 manualmente (re-correr generar_lista después del commit). El phase gate lo elimina para siempre: el sistema no permite ese error, independientemente de si el operador recuerda o no.
Build-time vs production
Distinción clave: disciplina de lectura del agente (build-time) ≠ sidecar/journal/incremental (production-time). El agente ahorra tokens con disciplina. El sistema ahorra costo con artefactos de código. Confundirlos lleva a implementar en el momento equivocado.
