El placeholder disfrazado de manual: por qué RECLAMO nunca se actualizaba

Un valor que el propio sistema auto-generó no es "trabajo manual" solo porque no está vacío. Este documento explica el error con un caso real (32 reclamos que se quedaron con el texto genérico "reclamo" durante un mes entero) y la regla que lo evita: preservar solo lo que un humano decidió y que no se puede recalcular.

El principio en una frase

Cuando un módulo preserva trabajo manual al re-correr, la pregunta correcta no es "¿este campo tiene algo escrito?" sino "¿lo escribió un humano y el sistema no lo puede recalcular?". Un valor por defecto que el propio programa auto-generó (aunque no esté vacío) no es trabajo manual — es un dato derivado, y debe poder actualizarse cada vez que su fuente cambia.

Trabajo manual real → nace de un juicio humano que ningún input registra. Si se pisa, se pierde para siempre. Sí hay que protegerlo.
Auto-poblado → se recalcula 100% desde otra columna con una fórmula fija. Si se pisa con el valor fresco, no se pierde nada — al revés, se corrige. No hay que protegerlo.

① El error — un placeholder que se congeló por un mes

En mesa_1.xlsx el cobrador a veces escribe primero la palabra suelta "reclamo" en COMENTARIO (para no perder el registro en el momento del cobro) y recién después, otro día, vuelve y completa el detalle real. 4b_reclamos detecta el reclamo la primera vez que ve CATEGORIA=reclamo y auto-puebla RECLAMO con lo que haya en ese momento en COMENTARIO — así sea solo la palabra "reclamo".

El código exacto del problema:

214det["RECLAMO"] = det["COMENTARIO"].fillna("").astype(str) # auto-poblado, puede ser solo "reclamo" 324if m["RECLAMO"]: # pregunta "¿hay algo?", no "¿es manual real?" 325 fila["RECLAMO"] = m["RECLAMO"] # preserva el placeholder para siempre

Causa raíz

La condición if m["RECLAMO"]: solo verifica si el campo no está vacío. Pero el auto-poblado de la línea 214 nunca deja el campo vacío — como mínimo, escribe lo que sea que haya en COMENTARIO en ese instante, aunque sea la palabra suelta "reclamo". Entonces la condición se vuelve verdadera desde la primera corrida y bloquea cualquier actualización futura, para siempre, aunque el input tenga después el detalle completo.

Por qué existía esta protección

Antes de que mesa_N.xlsx tuviera la columna CATEGORIA, el flujo era distinto: el cobrador solo escribía la palabra "reclamo" en el input, y el supervisor tipeaba el detalle completo directamente en reclamos_2026-07.xlsx (por eso el header dice "Reclamo — llenar a mano"). En ese mundo, cualquier texto en RECLAMO SÍ era trabajo humano real y merecía protegerse. La protección no es el error — quedó desactualizada cuando cambió el flujo de origen del dato.

② La solución — separar lo que se puede recalcular de lo que no

Con CATEGORIA ya en el input, el cobrador clasifica y escribe el detalle completo directo en mesa_N.xlsx. El dato ya no nace en el output — nace en el input. Por eso RECLAMO en el output debe dejar de tratarse como manual: tiene que reflejar siempre lo último que diga COMENTARIO. Lo que sigue siendo decisión exclusiva del supervisor —y que ningún input registra— son TIPO_RECLAMO, RESOLUCION, ESTADO y FECHA_RESOLUCION. Esos sí se preservan.

Cuál es la solución

En _aplicar_manual, sacar RECLAMO de la lista de campos que se copian desde existente. Dejar que siempre tome el valor recién calculado en detectados (el COMENTARIO más fresco de pagos_efectivo.xlsx). El header de la columna también se actualiza: ya no es "llenar a mano", es "detalle del cobrador" — de solo lectura para el supervisor.

Por qué funciona

Cada corrida, RECLAMO queda 100% derivado de una sola fuente (COMENTARIO), así que nunca puede desincronizarse: no hay copia vieja que proteger porque no hay nada que se pierda al recalcular. Los campos que sí importan proteger —las decisiones del supervisor— siguen intactos porque ninguna fuente los puede recrear.

La distinción que resuelve todo

Antes de escribir if campo: → preservar, preguntate de dónde viene el valor.

⚙ Auto-poblado

Se calcula con una fórmula fija a partir de otra columna (RECLAMO = COMENTARIO). Si se recalcula con el dato fresco, no se pierde nada — se gana precisión. No protejer.

🧑 Trabajo manual real

Nace de un juicio del supervisor que ningún input registra (ej. clasificar TIPO_RECLAMO como "convenio" o "medidor"). Si se pisa, se pierde para siempre — nadie lo puede reconstruir. Sí protejer.

③ De paso: ¿qué significa el guion bajo en _aplicar_manual?

En Python, un nombre que empieza con _ (un solo guion bajo) es una convención de lectura, no una restricción real del lenguaje. Le dice a cualquiera que lea el código: "esta función es un detalle interno de este archivo — no la llames desde otro módulo, no forma parte de lo que este archivo ofrece hacia afuera". El intérprete de Python no bloquea nada: técnicamente se podría importar y llamar igual. Es una señal para humanos (y para herramientas de linting), no un candado.

ConvenciónSignificadoEjemplo en 4b_reclamos/main.py
nombrePúblico — pensado para usarse también desde otros módulosleer_correcciones_lote()
_nombrePrivado por convención — implementación interna de este archivo_aplicar_manual(), _pres_key(), _cargar_existente()
__nombreDentro de una clase: activa "name mangling" para evitar choques al heredar (estilo POO, no se usa en jass_system que es todo funciones sueltas)—

_aplicar_manual es exactamente eso: un paso interno del pipeline de main.py — "tomá lo detectado este mes y fusionale encima las columnas que el supervisor ya trabajó". Nadie más en el sistema necesita llamarla directamente, por eso lleva el guion bajo.

Reglas para recordar

1. "Preservar trabajo manual" solo aplica a valores que un humano decidió y que el sistema no puede recalcular desde ninguna fuente. No a cualquier campo que no esté vacío.
2. Antes de escribir if campo: preservar(campo), preguntate: "si lo piso con el valor recién calculado, ¿pierdo una decisión humana, o gano precisión?". Si gana precisión, no lo protejas — dejalo recalcularse siempre.
3. Un placeholder auto-generado por el propio sistema (como RECLAMO="reclamo" desde el auto-poblado) no es trabajo manual aunque tenga texto adentro. Distinguí por origen del dato, no por si el campo está vacío.
4. Si el flujo de origen de un dato cambia (ej. el detalle del reclamo pasó de escribirse en el output a escribirse en el input con CATEGORIA), revisá si las reglas de preservación que dependían del flujo viejo siguen teniendo sentido — quedan obsoletas en silencio.
5. _nombre en Python (un guion bajo al inicio) es una convención de "uso interno de este archivo", no una restricción que el lenguaje haga cumplir — es una señal para quien lee el código, no un candado técnico.
