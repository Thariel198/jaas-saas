¿Por qué estos conceptos son de nivel senior?

Un junior escribe código que funciona hoy. Un medior escribe código que funciona la semana que viene. Un senior escribe código que funciona cuando algo falla, cuando la lista de beneficiarios cambia, cuando el sistema se corre dos veces, cuando nadie recuerda qué pasó hace 3 meses. Estos cinco patrones son las herramientas que hacen posible eso. No son conceptos teóricos — todos están implementados o en camino en jass_system, un sistema mensual de cobros de agua que no puede permitirse errores silenciosos.

Prerequisito: Idempotencia es la base — sin ella ningún otro patrón funciona correctamente.
Foundational (Día 1): Guard + Journal siempre desde el primer módulo.
Hardening (cuando el volumen lo justifica): Sidecar + Incremental cuando haya multi-JASS o >10k registros.

Los cinco patrones

🛡️

Guard

Centinela de precondición
Foundational · Día 1

Bloquea la ejecución con sys.exit(1) si una precondición falla. No es una advertencia — es un bloqueo completo. No existe la opción de "continuar de todos modos".

Diferencia con validación normal

Una validación avisa del problema. Un guard impide que el problema avance. El guard no confía en que el operador leyó el aviso.

En la industria

Pre-flight check · Precondition gate · CI/CD gate (test fallido bloquea deploy) · Guard clauses en programación funcional.

En jass_system
# aplicar_penalidad.py — phase gate if aplicados > 0: log.error("PHASE GATE: ciclo comprometido") sys.exit(1) # bloqueo total
📓

Journal

Libro de actas de operaciones
Foundational · Día 1

Log append-only de operaciones. Registra qué hice, cuándo, sobre qué registro. Nunca se edita — solo crece. El estado actual se reconstruye leyendo el journal de atrás hacia adelante.

Propiedad clave

Los eventos son primarios. El estado es derivado. Esto permite reconstruir cualquier estado pasado y auditar exactamente qué ocurrió.

En la industria

WAL (PostgreSQL) · Kafka topics · Libro diario contable (entrada doble) · Event Sourcing. El principio es idéntico en todos: nunca mutés el pasado.

En jass_system
# audit_penalidad.xlsx — el journal de 6_corte MZ | LT | OPERACION | MES_ANO | ACCION | A | 5 | SET_DEBE | 2026-06 | APLICADO | A | 5 | REVERTIDO | 2026-06 | REVERTIDO | # SET_TIENE = APLICADO - REVERTIDO
📎

Sidecar

Detector de cambio barato
Hardening · Cuando el volumen lo justifica

Archivo pequeño junto al archivo de datos que responde una sola pregunta: ¿cambió este archivo desde la última vez? — sin abrir el archivo grande.

Por qué importa

Leer el sidecar cuesta O(1) — 80 bytes, sin parsear. Leer el archivo de datos cuesta O(n) — 575 filas, Excel, memoria. El sidecar elimina el 99% del costo cuando el archivo no cambió.

En la industria

Kubernetes sidecar containers · Archivos .crc, .sha256 en ETL · HTTP ETag headers (mismo concepto, en red). El término nació en Kubernetes pero el patrón es universal.

Implementación típica
# planilla_2026-06.sidecar.json { "hash": "a3f9b2c1...", "n_filas": 575, "ts_modificado": "2026-06-24T09:15", "generado_por": "2_planilla" }
⚡

Incremental Processing

Solo el delta, siempre
Hardening · Cuando el volumen lo justifica

Solo procesar los registros nuevos o cambiados desde la última corrida. Combina sidecar (¿cambió el archivo?) y journal (¿qué registros ya procesé?) para calcular el delta.

Cómo funciona

1. Lee sidecar → si hash no cambió, sale limpio.
2. Lee journal → identifica qué registros ya están procesados.
3. Procesa solo los nuevos (delta).
4. Actualiza journal y sidecar.

En la industria

Kafka consumer offsets · Spark checkpoints · CDC (Change Data Capture) · ETL incremental loads. "Solo el delta" es la diferencia entre escalar y no escalar.

Cuándo agregar en jass_system

Hoy con 239 predios el costo de re-procesar todo es bajo. Aplicar cuando haya múltiples JASS en el mismo sistema o >10k registros por ciclo.

🔄

Idempotencia — el prerequisito de todo

La misma operación N veces = el mismo resultado que 1 vez
Foundational · Día 1

Una operación es idempotente si ejecutarla dos veces produce el mismo resultado que ejecutarla una vez. Es el prerequisito sin el cual ningún Guard, Journal, Sidecar ni Incremental funciona correctamente — porque todos ellos presuponen que re-ejecutar es seguro.

Idempotencia vs Reconciliación Bidireccional

La idempotencia evita duplicar. La reconciliación bidireccional garantiza que el archivo compartido siempre converja al estado correcto, aunque la lista de beneficiarios cambie entre corridas. La segunda es la evolución de la primera.

No idempotente vs Idempotente
# ❌ No idempotente — duplica al re-correr CORTE_RECONEXION += 40.0 # ✓ Idempotente — igual N veces if ejecutar == "SI": ws[f"M{row}"] = 40.0 # SET, no ADD
En jass_system

La reconciliación bidireccional (SET_DEBE vs SET_TIENE) hace que aplicar_penalidad.py sea idempotente Y convergente: si la lista cambia, la próxima corrida lo corrige automáticamente.

⚠️ Distinción crítica: build-time vs production-time

Build-time (construcción — ahora)

  • Audiencia: el agente de desarrollo (Claude Code)
  • Problema: tokens gastados en releer archivos que no cambiaron
  • Solución: disciplina de lectura — nrows, head(), no releer fuentes estáticas
  • Implementación: comportamiento del agente, no código
  • Costo si se ignora: sesiones más caras, contexto acumulado

Production-time (el sistema corriendo solo)

  • Audiencia: el agente de producción (SaaS), el pipeline mensual
  • Problema: costo de procesar archivos completos en cada ciclo
  • Solución: Sidecar + Journal + Incremental Processing
  • Implementación: código en el sistema — features permanentes
  • Costo si se ignora: sistema lento o costoso cuando escale

Conclusión: El sidecar no es un andamio de construcción que se tira cuando el sistema esté listo. Es una feature de producción cuyo beneficio secundario es también abaratar las verificaciones durante construcción. El mismo artefacto sirve a las dos audiencias — pero pertenece al código de producción. No implementar para ahorrar tokens ahora — implementar cuando la escala lo justifique.
