API: la caja negra con motivo

Encapsular código no alcanza para llamarlo "API" — cualquier función escondida cumpliría eso. Lo que realmente define una API es que protege a alguien de un cambio que va a pasar del otro lado de la caja negra.

diseño de seguimiento_repo.py

El principio en una frase

Una API es un contrato: "si me llamás con estos datos, siempre me voy a comportar así" — sin importar qué cambie por dentro. El encapsulamiento (esconder el código) es solo el mecanismo que hace posible cumplir esa promesa. No es el motivo.

Esconder código sin que nadie dependa de ese contrato no es una API — es solo una función privada a la que le pusiste un cartel de más.

La trampa: si "esconder" alcanzara, hola_mundo() sería API

El error natural es pensar "la escondo → ya es API". Pero comparando dos funciones igual de escondidas, una merece el nombre y la otra no:

hola_mundo()

print("Hola Mundo")

  • ¿Quién más la llama? Nadie, o solo el mismo script
  • ¿Va a cambiar por dentro? No — imprimir un string no tiene "por dentro" que evolucione
esconderla no protege a nadie de nada

registrar_cargo(mz, lt, concepto, monto)

valida → backup → escribe evento → audita

  • ¿Quién más la llama? Siembra inicial, 5_cobranza hoy, agente mañana, UI futura
  • ¿Va a cambiar por dentro? Sí — hoy Excel, mañana quizás otra base; hoy valida X reglas, mañana más
esconderla protege a los 4 callers del cambio

El test real, en 2 preguntas

Antes de llamar "API" a algo, hacer estas dos preguntas. Si las dos dan sí, vale la pena la caja negra. Si alguna da no, es solo una función normal.

¿Hay 2+ interesados
que la necesitan usar
sin coordinarse entre sí?
No solo "podría haber" — ya existen o son casi seguros a corto plazo.
+
¿Es probable que
el interior cambie
con el tiempo?
Storage, reglas de validación, proveedor externo — algo ahí adentro no es estático.

Dos analogías que lo anclan

1. El cajero automático que mueven de local. Sigue funcionando igual aunque cambie el edificio, el banco de datos de atrás, o el software interno — porque el contrato (metés tarjeta, sacás plata) nunca cambia para quien lo usa. Esa es la estabilidad que protege el API.

interior (puede cambiar)
servidor del banco · software · ubicación física
→
API (nunca cambia)
pantalla + botones + ranura de tarjeta
→
vos, usando el cajero
nunca te enterás de lo que cambió adentro

2. Tu propia JASS ya vende agua exactamente así. Tu red de captación, tanque y tubería es el interior — nadie de afuera lo ve. El caño con medidor de cada casa es el API: "abrí la llave, sale agua, no necesitás saber de qué río viene ni cómo se purificó". Y lo cobrás por uso medido (S/ por m³) — exactamente el modelo de Claude API o Google Maps API: no te venden el modelo/el motor, te dejan usarlo a través de un contrato fijo y cobran por lo que consumís.

La regla que queda

Encapsular es el mecanismo. Proteger a callers reales de un cambio probable es el motivo. Sin motivo, esconder código es cosmético.
Cobrar por una API (Claude, Google Maps) es una decisión de negocio aparte del concepto técnico — el mismo contrato puede ser gratis (registrar_cargo() dentro de jass_system) o pago, sin que cambie qué lo hace "API".
Aplicado a jass_system: seguimiento_repo.py es API pública porque ya tiene 4 callers reales y un interior que va a evolucionar. Ver shared/docs/diagrama_seguimiento_pueblo.html para el diseño completo.
