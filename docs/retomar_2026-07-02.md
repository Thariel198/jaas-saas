## 1. De dónde salió esto

La sesión arrancó con un objetivo distinto: sembrar "génesis de obligaciones" (multa/acuerdos/convenio)
para que julio facture bien. A mitad de camino se aclaró el problema real: **génesis es solo una foto de
arranque — no existía ningún lugar que llevara el historial de cuánto pagó cada predio cada mes**, para
esos 3 conceptos. Hoy esa información vivía a mano, dispersa en 3 archivos distintos
(`padron_secundario/reunion`, `.../faena`, `mayo-planilla/Cobro medidores`, `SEGUIMIENTO/NUEVAS
INSTALACIONES`), sin trazabilidad real.

Esto llevó a diseñar y construir **`seguimiento_pueblo`**: un sistema de seguimiento continuo (no solo un
saldo inicial) para MULTA, ACUERDOS_ASAMBLEA y CONVENIO. Reemplaza por completo la idea original de
"ledger de génesis aparte".

---

## 2. El diseño — en una frase

**Event-sourced, no saldo mutable.** Cada movimiento (deuda nueva, pago, corrección) es una fila que se
agrega a un registro — nunca se edita ni se borra una fila existente. El saldo de cualquier mes se calcula
sumando el historial, nunca se guarda como celda que alguien pueda pisar.

```
Eventos (append-only)                     Repo (único writer)
  CARGO   → deuda nueva                     shared/seguimiento_repo.py
  PAGO    → 5_cobranza registra el pago     registrar_cargo/pago/ajuste
  AJUSTE  → corrección manual               get_saldo / get_saldos_bulk
                                             estado_cuenta / generar_vista
                    ↓
    shared/seguimiento_pueblo.xlsx (la fuente — nunca se edita a mano)
                    ↓
    shared/vista_seguimiento_pueblo.xlsx (pivot regenerable, lo que lee un humano)
```

**Decisiones clave, con el motivo:**
- **La llave es `(MZ, LT)`, no la persona.** Se consideró seguir a la persona (por si hay reasignación de
  lote) pero se descartó — fue un caso puntual del pasado (16 lotes, ya resuelto), no un patrón recurrente.
  Sobreingeniería evitada (Regla del Tres aplicada a modelado, no solo a código).
- **Convenio = suma de 2 fuentes** (`medidor_saldo.xlsx` + `inscripcion_saldo.xlsx`, ambas en
  `shared/genesis_inputs/`), **no la cuota S/25** que aparecía antes — esa cuota era un bug de visibilidad
  parcial del sistema viejo, no la deuda real.
- **6 predios de instalación excluidos** de `seguimiento_pueblo` para CONVENIO (B-20, C-43, C-35, F1-11,
  G-21, W-2) — su deuda ya está completa en `arrastre_consolidado`, no se duplica.
- **5_cobranza reconcilia por delta**, no por evento-por-pago — porque recalcula el mes completo en cada
  corrida (no procesa pago a pago). Cada corrida compara "lo que calculó fresco" contra "lo que ya está
  anotado" y solo agrega la diferencia.

Razonamiento completo, con las alternativas descartadas y el motivo de cada una:
**`docs/decisiones/seguimiento_pueblo.md`** ← el documento más completo, léelo si algo de esto no cierra.

## 5. Los 3 bugs que aparecieron al verificar con datos reales (y cómo se arreglaron)

1. **Escritura no atómica.** Un `wb.save()` directo puede dejar un `.xlsx` corrupto si el proceso se corta
   a mitad de camino — pasó una vez de verdad en una corrida real. Fix: escribir a un archivo temporal y
   recién reemplazar con `os.replace()` (atómico). Con retry ante `PermissionError` transitorio de Windows
   (pasó también, un antivirus/indexador bloqueando el archivo un instante).
2. **Fecha de siembra mal puesta.** La siembra usaba `MES=2026-07`, pero 5_cobranza sigue procesando el
   ciclo `2026-06` (julio bloqueado por D3 — ver abajo). Como el saldo se calcula filtrando "eventos con
   MES ≤ mes consultado", el cargo de julio quedaba invisible al preguntar "¿cuánto debía a fin de junio?"
   → saldo salía negativo. Fix: `MES_SIEMBRA = "2026-06"`, re-sembrado desde cero (no se puede editar la
   fecha de un evento ya escrito — append-only).
3. **Faltaba la exclusión de los 6 predios de instalación en la reconciliación.** La siembra sí los excluía,
   pero `5_cobranza` no lo sabía — le creó un pago de CONVENIO a B-20 sin cargo correspondiente (saldo
   negativo falso). Fix: la lista de exclusión se centralizó en `seguimiento_repo.py` (antes solo vivía en
   el script de siembra) y ambos lados la usan. La 1 fila mala ya escrita se corrigió a mano con backup
   (mismo patrón que se usó para el bug B7 en su momento) — es un artefacto de bug, no un evento real que
   el append-only tenga que proteger.

**Deuda menor, no bloquea nada:**
- `6_corte/seguimiento.py` y `6b/seguimiento_multas.py` no se re-corrieron tras estos cambios (mismo
  criterio que se usó con B7 — no mutar estado cerrado de junio innecesariamente).
- Performance: cada evento hace un read+write completo del archivo (crece con el tamaño). La siembra +
  reconciliación completa de hoy tardó ~20 min para ~1700 eventos. Alcanza para el volumen mensual actual
  (~700-1000 eventos/mes); si crece mucho más, convendría batch-write.
